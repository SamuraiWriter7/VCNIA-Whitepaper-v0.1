# VCNIA Glossary

## Glossary for Value-Circulating Network Intelligence Architecture

This glossary defines key terms used in **VCNIA: Value-Circulating Network Intelligence Architecture**.

VCNIA is based on the following core stack:

```text
Existence Proof → Gratitude → Trust → Royalty / Value Allocation → Network Intelligence

Its core principle is:

Intelligence emerges where value circulates.
1. VCNIA

VCNIA stands for Value-Circulating Network Intelligence Architecture.

It is a conceptual and technical architecture for describing how intelligence can emerge from networks where traces, gratitude, trust, and value allocation circulate together.

VCNIA shifts the focus of intelligence from isolated reasoning ability to networked value circulation.

2. Value-Circulating Network Intelligence Architecture

The full name of VCNIA.

It refers to an architecture in which value flows through four primary layers:

Existence Proof
Gratitude
Trust
Royalty / Value Allocation

When these layers interact, the network can become more adaptive, stable, and intelligent.

3. Kazene Model of Network Intelligence

The theoretical and philosophical foundation behind VCNIA.

The Kazene Model explains why network intelligence may emerge from circulation, traceability, recognition, trust, and value return.

VCNIA is the architectural implementation of this model.

Kazene Model = theoretical foundation
VCNIA        = architectural implementation
4. Value Circulation OS Stack

The four-layer OS-like structure used by VCNIA.

Existence Proof OS
      ↓
Gratitude OS
      ↓
Trust OS
      ↓
Royalty OS

This stack defines how contribution becomes traceable, recognizable, trustworthy, and returnable as value.

5. Existence Proof OS

The first layer of the VCNIA stack.

Existence Proof OS records that a trace exists.

It answers:

What existed, when, and in what context?

It does not determine ownership, legal rights, or reward.
It only records existence and provenance.

6. Gratitude OS

The second layer of the VCNIA stack.

Gratitude OS records that a trace has been recognized, appreciated, referenced, or used.

It answers:

What contribution was recognized as meaningful?

In VCNIA, gratitude is treated as the first active signal of value circulation.

7. Trust OS

The third layer of the VCNIA stack.

Trust OS accumulates gratitude, verification, and contribution history into structured trust.

It answers:

Which contributors, traces, agents, or systems have demonstrated structural reliability?

Trust in VCNIA is not popularity.
It is accumulated structural reliability.

8. Royalty OS

The fourth layer of the VCNIA stack.

Royalty OS returns value to contributors according to trace records, gratitude events, trust profiles, and allocation policy.

It answers:

How should value return to contributors?

In VCNIA, royalty does not only mean money.
It means any structured return of value.

9. Value Allocation Layer

The architectural name for the Royalty OS layer.

This layer allocates value based on contribution records, recognition signals, trust, and governance rules.

Possible value types include:

money
credits
points
reputation
access rights
visibility
governance weight
royalty shares
citation priority
non-transferable gratitude tokens
10. Trace

A trace is any recordable sign of contribution, influence, presence, or participation.

Examples include:

idea
text
prompt
design
code
dataset
review
decision
AI-generated output
human-authored input
transformation
protocol specification

A trace is the smallest unit of VCNIA value circulation.

11. Trace Record

A structured record that proves or records the existence of a trace.

A trace record may include:

trace_id
creator_id
timestamp
content_hash
provenance
source_uri
context
signature
metadata

In VCNIA, trace records are created in the Existence Proof Layer.

12. Trace ID

A unique identifier for a trace.

Example:

trace_vcnia_001

A trace ID allows later gratitude, trust, and value allocation events to reference the trace.

13. Provenance

Information about the origin, source, creation process, or registration method of a trace.

Provenance helps answer:

Where did this trace come from?
How was it created?
What influenced it?

Provenance may include parent traces, source references, authorship context, or registration method.

14. Content Hash

A cryptographic or semi-cryptographic fingerprint of content.

Example:

sha256:examplehash1234567890abcdef

A content hash helps verify that a trace has not been changed.

In VCNIA v0.1, content hash is optional, but later versions may make it more important.

15. Signature

A cryptographic or semi-cryptographic proof attached to a record.

A signature may help verify:

who created the record,
whether the record was modified,
whether the record is authentic.

In VCNIA v0.1, signatures are optional.

16. Gratitude Event

A structured record showing that a trace was recognized, appreciated, referenced, or used.

A gratitude event may include:

gratitude_id
trace_id
sender_id
receiver_id
gratitude_type
impact_score
message
timestamp
verification_status

Gratitude events are created in the Gratitude Layer.

17. Gratitude ID

A unique identifier for a gratitude event.

Example:

gratitude_vcnia_001

A gratitude ID allows trust and value allocation layers to reference a recognition event.

18. Gratitude Receipt

A portable record of gratitude or recognition.

A gratitude receipt may show:

who recognized a contribution,
which trace was recognized,
why it mattered,
when it was recognized.

A gratitude receipt is usually non-monetary.

19. Impact Score

A numerical score representing the recognized impact of a trace.

In current VCNIA schemas, impact_score is usually normalized from 0.0 to 1.0.

Example:

0.82

An impact score should be treated carefully.
It is a recognition signal, not an absolute measure of value.

20. Recognition Signal

A signal that indicates a trace had meaning, usefulness, influence, or impact.

Gratitude events are the primary recognition signals in VCNIA.

Recognition signals may later contribute to trust formation.

21. Trust Event

A structured record showing a change in trust.

A trust event may include:

trust_event_id
subject_id
related_trace_ids
related_gratitude_ids
trust_delta
trust_score_after
reason
verification_status
risk_flags

Trust events are created in the Trust Layer.

22. Trust Profile

An accumulated trust state for a contributor, trace, AI agent, system, or project.

A trust profile may include:

overall trust score
originality
reliability
usefulness
integrity
citation quality
verification quality
long-term value
network contribution

A trust profile should be dynamic, reviewable, and context-dependent.

23. Trust Delta

The change in trust caused by a trust event.

Example:

trust_delta: 0.04

Positive values increase trust.
Negative values decrease trust.

Trust delta should be interpreted in context.

24. Trust Score

A normalized representation of accumulated trust.

In current VCNIA examples, trust scores are often represented between 0.0 and 1.0.

A trust score should not be treated as a complete measure of human worth or final authority.

It is only a structured reliability signal within a specific system.

25. Trust Dimensions

Different aspects of trust used by Trust OS.

Examples include:

originality
reliability
usefulness
integrity
citation quality
verification quality
long-term value
network contribution
collaboration quality
governance alignment

Dimensional trust is preferred over a single simplistic reputation score.

26. Trust Decay

A process by which trust decreases over time or under certain conditions.

Trust decay may occur when:

contribution becomes outdated,
verification weakens,
risk increases,
no new contribution occurs,
governance rules change.

Trust decay helps prevent old trust from dominating future value allocation.

27. Trust Recovery

A process by which trust can be restored or improved after decline.

Trust recovery may occur through:

verified new contributions,
correction of errors,
dispute resolution,
improved transparency,
better citation quality,
reduced abuse signals.

Trust should be dynamic, not permanently punitive.

28. Risk Flag

A structured warning signal attached to a record.

Examples include:

possible_spam
possible_sybil_attack
possible_trust_farming
possible_false_gratitude
possible_identity_spoofing
possible_attribution_laundering
disputed_claim

Risk flags help governance systems identify possible abuse.

29. Value Allocation Event

A structured record showing that value was allocated to a contributor, system, project, or agent.

A value allocation event may include:

allocation_id
recipient_id
source_trace_ids
related_gratitude_ids
related_trust_event_ids
value_type
amount
allocation_rule
timestamp

Value allocation events are created in the Royalty / Value Allocation Layer.

30. Allocation ID

A unique identifier for a value allocation event.

Example:

allocation_vcnia_001

An allocation ID allows audit trails and dispute resolution.

31. Value Type

The type of value being allocated.

Examples include:

monetary
credit
point
reputation
access
visibility
governance
royalty_share
citation_priority
gratitude_token
ai_readable_status

VCNIA does not require value to be monetary.

32. Allocation Rule

The rule used to determine how value is allocated.

Examples include:

equal_split
trace_weighted
gratitude_weighted
trust_weighted
hybrid_weighted
governance_defined
manual_review
decay_adjusted
long_term_weighted

Allocation rules should be transparent and auditable.

33. Royalty Pool

A reserved pool of value that can be distributed to contributors.

A royalty pool may contain:

money
credits
points
tokens
reputation units
access rights
governance weight

The pool does not have to be monetary.

34. Value Return

The process by which value flows back to contributors.

Value return may be monetary or non-monetary.

In VCNIA, value return is necessary to complete the circulation loop.

Creation → Trace → Gratitude → Trust → Value Return → New Creation
35. Value Circulation

The continuous flow of value through the VCNIA stack.

Trace → Recognition → Reliability → Return → Intelligence

Value circulation prevents value from being trapped or extracted without return.

36. Network Intelligence

Intelligence that emerges from a network of traces, recognition signals, trust structures, value allocation mechanisms, and feedback loops.

VCNIA defines intelligence as:

A network structure that generates traces, evaluates the traces of others, forms trust, and circulates value.

Network intelligence is not located in a single model or individual.

It emerges through circulation.

37. Network Intelligence Signal

A possible future event or metric indicating that the network has become more adaptive, stable, or intelligent through circulation.

Examples may include:

better contribution discovery,
improved trust accuracy,
fairer value allocation,
reduced manipulation,
stronger collaboration,
more sustainable creation.

This term is not yet formally defined in v0.1.

38. AI Agent

An AI system, model, workflow, or autonomous/semi-autonomous process that can participate in VCNIA.

An AI agent may:

create traces,
issue gratitude,
evaluate trust,
recommend allocation,
participate in multi-agent workflows.

AI agents require careful identity and governance design.

39. Human Contributor

A human who creates, registers, reviews, verifies, recognizes, or receives value from traces.

VCNIA should protect human dignity and privacy.

Human contributors should not be reduced to a single mechanical score.

40. AI-to-AI Gratitude

A gratitude event issued by one AI agent to another AI agent or to a trace produced by another AI agent.

This may become important in future multi-agent networks.

AI-to-AI gratitude should be governed carefully to avoid automated trust inflation.

41. Human-AI Collaboration

A collaborative process in which humans and AI systems jointly create, evaluate, verify, or circulate value.

VCNIA is designed to support human-AI networks without treating AI as merely isolated tools or humans as passive data sources.

42. Governance

The rules and processes that determine how VCNIA records are created, verified, disputed, updated, and used.

Governance may define:

who can create trace records,
who can issue gratitude,
how trust is calculated,
how value is allocated,
how disputes are handled,
how privacy is protected,
how AI agents are identified.

Governance is part of the architecture, not an optional decoration.

43. Governance Policy

A specific set of rules used by a VCNIA-compatible implementation.

Governance policies may define:

allocation rules,
trust rules,
verification rules,
appeal processes,
privacy rules,
agent permissions.

Governance policies should be transparent and versioned.

44. Verification Status

A field indicating whether a record has been verified.

Examples include:

unverified
self_attested
system_verified
human_verified
multi_source_verified
disputed
rejected

Verification status does not guarantee truth.
It only indicates the current verification state.

45. Self-Attested

A record that is asserted by the creator or issuer without independent verification.

Self-attested records can be useful, but should not be treated as fully verified.

46. System-Verified

A record that has been checked by an automated system.

System verification may include schema validation, hash checks, timestamp checks, or consistency checks.

System-verified does not necessarily mean human-verified.

47. Human-Verified

A record that has been reviewed or confirmed by a human.

Human verification may be useful for high-impact or disputed records.

48. Multi-Source Verified

A record that has been confirmed through multiple sources.

This is stronger than self-attestation or single-source verification.

49. Dispute

A challenge to the validity, accuracy, fairness, or interpretation of a VCNIA record.

Disputes may involve:

trace attribution,
gratitude validity,
trust scoring,
allocation amount,
identity claims,
provenance accuracy.

Dispute resolution is essential for high-stakes implementations.

50. Dispute Status

A field indicating the current state of a dispute.

Examples include:

none
open
under_review
resolved
rejected
appealed
51. Audit Trail

A reviewable chain of records showing how an outcome was reached.

For value allocation, an audit trail may look like:

value_allocation_event
  → trust_profile
  → trust_events
  → gratitude_events
  → trace_records

Audit trails support transparency and accountability.

52. Schema

A formal structure defining what fields a record should contain.

VCNIA uses JSON Schemas to define valid event structures.

Current v0.1 schemas include:

trace-record-v0.1.schema.json
gratitude-event-v0.1.schema.json
trust-event-v0.1.schema.json
value-allocation-v0.1.schema.json
53. Sample

An example file that demonstrates a valid schema-compatible record.

Samples help test whether schemas work correctly.

Current v0.1 samples include:

trace-record.sample.json
gratitude-event.sample.json
trust-event.sample.json
value-allocation.sample.json
54. Schema Validation

The process of checking whether a sample file matches a JSON Schema.

Schema validation confirms structural correctness.

It does not confirm:

legal validity,
factual truth,
authorship authenticity,
fairness of allocation,
correctness of trust,
absence of manipulation.
Schema-valid does not mean truth-verified.
55. Compliance Test

A future test system that may check whether implementations follow VCNIA rules.

Compliance tests may include:

valid samples,
invalid samples,
edge cases,
abuse scenarios,
governance checks,
privacy checks.

This is planned beyond v0.1.

56. Sybil Attack

An attack in which one actor creates many fake identities to manipulate a network.

In VCNIA, Sybil attacks may affect:

gratitude events,
trust scores,
value allocation,
governance voting.

Sybil resistance is important for future implementations.

57. Trust Farming

A manipulation pattern where actors artificially generate trust signals.

Trust farming may involve:

fake gratitude,
collusive accounts,
circular recognition,
bot-generated reputation,
repeated low-quality interactions.

Trust OS should include safeguards against trust farming.

58. Attribution Laundering

A manipulation pattern where someone attempts to make a copied or derived contribution appear original.

Attribution laundering may involve:

false provenance,
missing parent traces,
fake trace registration,
hiding source influence.

Existence Proof OS and governance rules should reduce this risk.

59. False Gratitude

A gratitude event that is misleading, artificial, collusive, or not based on real impact.

False gratitude can distort trust and value allocation.

Gratitude OS should treat recognition as a signal, not final proof.

60. Value Extraction

A pattern where value is taken from contributors or traces without meaningful return.

VCNIA is designed to reduce one-way extraction by enabling value return.

61. Non-Monetary Value

Value that is not direct money.

Examples include:

recognition,
attribution,
credits,
badges,
access rights,
visibility,
governance participation,
AI-readable contribution status.

Non-monetary value is important for early VCNIA implementations.

62. Monetary Value

Direct financial value.

Examples include:

payments,
royalties,
revenue share,
monetary credits.

Monetary value allocation requires legal, tax, and compliance review.

VCNIA does not automatically provide such legal infrastructure.

63. AI-Readable Attribution

Attribution metadata designed to be read and processed by AI systems.

AI-readable attribution may help future AI systems understand:

who contributed,
what trace was used,
how value should return,
what provenance exists.
64. Contributor Dignity

A principle that contributors should not be reduced to opaque scores, extractive metrics, or surveillance records.

VCNIA should support human and AI contribution while preserving fairness, privacy, and context.

65. Plural Value Systems

The idea that different communities may define value differently.

VCNIA should not impose a single universal value model.

Different implementations may prioritize:

creativity,
accuracy,
usefulness,
care,
originality,
long-term contribution,
open-source maintenance,
governance participation.
66. Circulation Loop

The repeating cycle at the heart of VCNIA.

Creation → Trace → Gratitude → Trust → Value Return → New Creation

The circulation loop is what transforms isolated contribution into network intelligence.

67. Core Formula

The shortest expression of VCNIA:

Trace → Recognition → Reliability → Return → Intelligence

Or:

Existence Proof → Gratitude → Trust → Royalty → Network Intelligence
68. Closing Definition

VCNIA can be summarized as follows:

VCNIA is an architecture for transforming contribution into trace, trace into recognition, recognition into trust, trust into value return, and value return into network intelligence.
